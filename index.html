Overview

소상공인의 사업자·금융 정보를 기반으로 신청 가능한 지원사업과 대출을 탐색하고, 필요한 자금에 맞는 상품 조합을 추천하는 서비스입니다. 신청 단계에서는 필요한 서류를 안내하고 HWPX 신청서 자동 작성과 제출 서류 검증을 지원하며, 이후 대출 상환 관리까지 하나의 서비스에서 제공합니다.

Architecture

Spring Boot가 인증·사업자·신청·자금 조합 등 서비스 로직을 담당하고 PostgreSQL·Redis와 금융 API를 연동합니다. FastAPI AI 서버는 지원사업 판정·서류 처리·Document Agent 기능을 담당하며, Spring Boot는 인증된 사용자의 요청과 작성 대상 Template을 검증한 뒤 문서 생성 요청을 전달합니다.

Key Implementations

01

Spring Boot–FastAPI 문서 생성 경계

작성 가능한 문서와 최신 완료 Template을 먼저 확인한 뒤 FastAPI Document Agent에 생성을 요청하도록 구성했습니다. 장시간 진행될 수 있는 LLM·파일 생성 작업 동안 DB Transaction을 유지하지 않도록 데이터 조회와 외부 I/O의 경계를 분리했습니다. 또한 생성 결과의 문서·Template ID, UUID, 파일명, MIME Type과 비어 있지 않은 본문을 검증한 후 사용자에게 HWPX 파일을 전달합니다.

02

Source Registry 기반 데이터 접근 분리

LLM의 Field 의미 분석과 실제 사용자 데이터 조회 책임을 분리했습니다. DIRECT·COMPUTED·GENERATED·USER_INPUT으로 Source 유형을 구분하고, 직접 조회·계산·문장 생성·사용자 직접 입력의 처리 정책을 각각 분리했습니다.

03

HWPX 구조 보존 Writer

신청서의 물리적 작성 위치를 기준으로 필요한 값만 최소 수정하고 기존 Paragraph·Run·Style 구조는 최대한 보존했습니다. 작성 전 대상 구조를 검증하고 생성 후에는 HWPX를 다시 파싱해 기대 문자열과 실제 결과를 대조합니다.

04

지원금·대출 통합 자금 조합 추천

서로 다른 지원사업과 대출 상품을 FundingCandidate라는 공통 모델로 추상화하고, 최대 3개 상품 조합에서 최소·최대 가능 금액을 검사했습니다. 지원금을 우선 배정하고 이후 저금리 대출을 배치해 총상환액·월납입액·평균금리 등을 기준으로 추천 조합을 제공합니다.

05

금융망 공통 Client 구조

금융 API별 Request·Response DTO는 도메인에 맞게 분리하면서 공통 Header 생성과 HTTP 요청, 업무 성공 코드 검증은 공통 Client로 구성했습니다. 이를 계좌·대출·상환 API에서 재사용했습니다.

Document Agent

신청서 전체 작성을 LLM에 맡기지 않고, 문서의 물리 구조 분석·Field 의미 판단·실제 데이터 조회·문서 쓰기 책임을 단계별로 분리했습니다. LLM은 Field의 의미와 Source를 판단하고, 실제 값은 검증된 Source Registry를 통해 조회하거나 계산한 뒤 Writer가 원본 HWPX 구조에 반영합니다.

Source Policy

Field의 의미를 분석하는 책임과 실제 값을 가져오는 책임을 분리하고, 값의 성격에 따라 Source 처리 정책을 구분했습니다.

DIRECT

사용자·사업자 정보처럼 DB에서 직접 조회할 수 있는 값

대표자명 · 사업자번호 · 주소
COMPUTED

여러 데이터를 조합하거나 기간 조건에 따라 계산해야 하는 값

최근 N개월 매출 · 기간별 합계
GENERATED

검증된 구조화 데이터를 근거로 문장을 생성해야 하는 값

사업 내용 · 서술형 작성 항목
USER_INPUT

자동으로 결정하지 않고 사용자가 직접 입력해야 하는 값

서명 · 동의 · 확인이 필요한 정보

LLM이 실제 값을 임의로 생성해 Writer에 전달하지 않고, 정의된 Source 정책과 검증을 통과한 데이터만 문서 작성 단계에서 사용하도록 구성했습니다.

Troubleshooting

Case 01 · Document Structure

단일 빈 문단을 전제로 한 Writer를 실제 HWPX의 다중 문단 구조까지 확장했다.

Problem
초기 Writer는 작성 대상 Cell에 빈 Paragraph가 하나만 존재한다고 가정했습니다. 하지만 실제 신청서에는 화면상 하나의 빈 Cell처럼 보여도 여러 개의 빈 Paragraph와 Run으로 구성된 영역이 있었고, 이러한 문서에서는 TARGET_STRUCTURE_UNSUPPORTED 오류가 발생했습니다.
Analysis
HWPX에서는 화면에 보이는 하나의 Cell과 XML 내부의 Paragraph 구조가 일치하지 않을 수 있음을 확인했습니다. 값을 작성하기 위해 Cell 전체를 다시 구성하면 기존 Run·Style이나 서식 구조가 손상될 가능성도 있었습니다.
Decision
여러 Paragraph를 하나로 합치거나 Cell 전체를 재생성하지 않고, 실제 작성 대상이 맞는지 먼저 검증한 뒤 필요한 Paragraph만 최소 수정하기로 했습니다.
Implementation
Parser 결과와 실제 Paragraph 구조를 대응시키고 모든 Paragraph가 비어 있는지 확인했습니다. 이후 첫 번째 대상 Paragraph에만 값을 삽입하고 나머지 빈 Paragraph와 Run·Style은 유지했습니다. 작성 후에는 생성된 HWPX를 다시 파싱해 기대 문자열과 실제 결과를 비교하도록 검증 절차를 추가했습니다.
Result
기존에 처리하지 못했던 여러 빈 Paragraph로 구성된 작성 영역까지 지원하도록 Writer를 확장했고, 원본 서식 구조를 최대한 유지하면서 값을 삽입할 수 있게 했습니다.
What I learned
문서 포맷을 처리할 때 화면에 보이는 형태를 기준으로 구조를 가정하기보다 실제 파일 내부의 물리 구조를 확인하고, 변경 범위를 최소화하는 것이 중요하다는 점을 배웠습니다.

Case 02 · LLM Reliability

LLM의 잘못된 Schema 응답이 후속 시스템으로 전파되지 않도록 Validation과 제한된 Repair를 적용했다.

Problem
Field 의미 분석 과정에서 LLM이 서로 역할이 다른 Enum 항목을 혼동해 Schema에 정의되지 않은 값을 반환하는 문제가 발생했습니다. 잘못된 응답을 그대로 저장하면 Source 조회와 Writer 단계까지 오류가 전파될 수 있었습니다.
Analysis
Prompt를 보완하는 것만으로는 동일한 형식 오류가 다시 발생하지 않는다고 보장할 수 없었습니다. LLM 응답 역시 외부 시스템에서 들어오는 입력이므로 모델이 생성했다는 이유만으로 신뢰 가능한 데이터로 취급해서는 안 된다고 판단했습니다.
Decision
Prompt 개선과 별개로 애플리케이션 레벨에서 명확한 Schema 계약을 정의하고, 검증을 통과한 결과만 후속 단계에서 사용할 수 있도록 구성했습니다.
Implementation
Pydantic으로 Enum·Candidate ID·Source Type·Source Key 등 응답 구조를 검증했습니다. 검증 실패 시 오류 위치, 받은 값, 허용 가능한 값을 포함한 Repair 요청을 생성하고 전체 후보에 대해 한 번만 재응답하도록 제한했습니다. Repair 결과 역시 동일한 Schema 검증을 다시 통과해야 저장되도록 했습니다.
Result
정의되지 않은 Schema 값이 DB와 Writer 단계로 그대로 전달되는 경로를 차단하고, 복구 가능한 오류만 제한적으로 다시 요청하는 구조를 만들었습니다.
What I learned
LLM 출력 역시 검증이 필요한 외부 입력이며, 생성 품질을 Prompt에만 의존하지 않고 시스템 계약과 실패 정책으로 제어해야 한다는 점을 배웠습니다.

Troubleshooting

Case 01 · Performance

Redis 캐싱 적용 후 동일 조건으로 다시 검증하고, 더 높은 부하에서 새 한계를 찾았다.

성능 개선 결과
87.8% → 63.0%600 VU CPU 사용률 · 캐싱 적용 전후
24.8%pCPU 사용률 감소 폭
800 VU응답시간·CPU·Run Queue가 다시 급증한 새 포화 구간
Problem
사용자 행동 기반 테스트에서 600 VU 구간의 서버 CPU 사용률이 약 87.8%까지 상승했다.
Analysis
대시보드·스터디·리포트 등 반복 조회 비중이 높은 흐름을 확인하고, 변경 빈도가 낮은 데이터가 요청마다 조회 로직과 DB 접근을 반복한다고 판단했다.
Decision
조회 경로 전체를 변경하기보다 반복 조회 데이터를 Redis 캐시에 두고 동일 데이터 요청의 DB 접근과 기존 조회 로직을 줄이는 방향을 선택했다.
Implementation
주요 조회 데이터에 캐싱을 적용한 뒤 동일한 600 VU로 재테스트했다. 개선 후 700·800 VU까지 부하를 확장했다.
Result
600 VU CPU 사용률 약 87.8% → 63.0% 수준, 24.8%p 감소. 800 VU 부근에서 평균 응답 142.2ms·p95 230ms·CPU 평균 87.1%·Run Queue 11.91로 다시 포화 징후를 확인했다.
What I learned
성능 개선은 한 번의 수치 개선으로 끝내지 않고, 동일 조건 재검증과 부하 확대를 통해 새로운 병목을 다시 찾는 과정까지 포함해야 한다.

Case 02 · AI Cost

작은 문서 수정까지 전체 AI 분석을 발생시키던 구조를 조건부 재분석 방식으로 바꿨다.

Problem
오탈자·띄어쓰기 같은 작은 수정에서도 전체 문서를 GMS에 다시 보내 LLM 토큰이 반복 소비됐다.
Analysis
문서를 여러 번 다듬는 실제 사용 패턴에서는 수정 발생 = 항상 재분석 구조가 호출 횟수와 비용을 누적시킨다고 판단했다.
Decision
문자열 표현 차이로 인한 오판을 줄이기 위해 먼저 Unicode NFC 정규화를 적용하고, Levenshtein Distance로 변경 비율을 계산하기로 했다.
Implementation
변경 비율 10% 이상일 때만 재분석 이벤트를 발생시키고, 분석 작업은 문서 저장 요청과 분리해 이벤트 기반 비동기로 처리했다.
Result
작은 수정마다 전체 분석을 반복하던 구조를 의미 있는 수준의 변경이 있을 때만 재분석하는 구조로 변경했다. 정확한 토큰 절감률은 측정하지 않았다.
What I learned
AI API 연동에서도 기능 호출 자체보다 비용과 호출 빈도를 애플리케이션 레벨 정책으로 제어하는 것이 중요하다.

Case 03 · Network

Webhook Timeout을 전체 시스템 문제가 아닌 네트워크 구간 문제로 나눠 범위를 좁혔다.

Problem
Docker Container의 LiveKit이 Host의 Spring Boot Webhook Endpoint로 요청할 때 host.docker.internal 연결이 Timeout됐다.
Analysis
LiveKit Container → Docker Host → Nginx → Spring Boot로 경로를 나누고 각 구간의 접근 가능 여부와 Endpoint 도달 여부를 확인했다.
Decision
Docker 내부 주소에 직접 의존하지 않고 외부 HTTPS Domain과 Nginx Reverse Proxy를 통하는 경로로 재구성했다.
Implementation
Webhook 목적지를 외부 HTTPS 경로로 변경하고 Spring Boot Endpoint의 HTTP 응답을 단계적으로 확인했다.
Result
LiveKit 이벤트가 Nginx를 거쳐 Spring Boot까지 전달되는 경로를 구축했다.
What I learned
복합 네트워크 문제는 한 번에 설정을 바꾸기보다 요청 경로를 구간별로 검증하면 원인 범위를 더 빠르게 좁힐 수 있다.

Case 04 · Business Logic

세션 종료와 평가 데이터의 완결성을 연결했다.

Problem
방장이 먼저 나가면 세션이 종료되어, 아직 평가를 제출하지 않은 참여자가 상호평가를 작성할 수 없었다.
Analysis
세션 상태 변화와 평가 완료 여부가 서로 독립적으로 처리되어 사용자 조작 순서에 따라 데이터가 누락될 수 있었다.
Decision
세션 종료 전 각 참여자가 본인을 제외한 모든 참여자에게 평가를 작성했는지 서비스 레벨에서 검사하도록 했다.
Implementation
전체 완료 시 true, 미완료 시 false와 미제출 사용자 정보를 반환하는 API를 구현했다.
Result
프론트가 종료 전에 미작성 참여자를 확인할 수 있어 조기 종료로 인한 평가 데이터 누락을 방지할 수 있게 했다.
What I learned
CRUD 외에도 서비스 상태 전환이 데이터 완결성에 미치는 영향을 비즈니스 로직으로 연결해야 한다.

Analysis
인증번호는 애플리케이션 인스턴스의 생명주기와 분리되고 일정 시간 후 자동 만료되어야 하는 임시 상태였다.

Case 03 · Cache Design

반복 조회되는 인기 상품을 요청마다 다시 계산하지 않도록 캐싱했다.

Problem
여러 사용자가 동일한 인기 상품 데이터를 반복 조회하는데 요청마다 DB 조회·계산이 반복될 수 있었다.
Analysis
인기 상품은 일반 실시간 데이터보다 변경 주기가 짧지 않아 모든 요청에서 동일 연산을 수행할 필요가 없다고 판단했다.
Decision
일정 주기로 캐시를 갱신하고 일반 조회에서는 Redis 결과를 우선 사용하도록 했다.
Implementation
캐시 미스 시 DB 조회 → Redis 저장 → 결과 반환 fallback을 구성했다.
Result
반복 조회 경로와 DB 조회 로직을 분리한 캐시 구조를 직접 설계·적용했다.
What I learned
캐시는 무조건 적용하기보다 데이터 변경 빈도와 반복 조회 패턴을 기준으로 선택해야 한다.
